## 🚀 コントリビューションの方法

次の方法で貢献できます。

- **バグ報告**: GitHub Issues で問題を報告する
- **機能提案**: GitHub Issues で新機能のアイデアを提案する
- **コードの提出**: プルリクエストでコードの改善を提出する
- **ドキュメントの改善**: プロジェクトドキュメントの改善に協力する
- **質問への回答**: Issues で他のユーザーを手助けする

本プロジェクトに参加する際は、すべてのコントリビューターを尊重し、建設的な批判を受け入れ、プロジェクトにとって最善となることに注力してください。

## 🛠️ 開発環境のセットアップ

### 前提条件

- Go 1.27 以上
- Redis（テスト用）
- Git

### クイックスタート

```bash
# 1. プロジェクトをフォークしてクローン
git clone https://github.com/your-username/warden.git
cd warden

# 2. アップストリームリポジトリを追加
git remote add upstream https://github.com/soulteary/warden.git

# 3. 依存関係をインストール
go mod download

# 4. テストを実行
go test ./...

# 5. ローカルでサービスを起動（Redis が動作していることを確認）
go run .
```

## 📝 コード規約

次のコード規約に従ってください。

1. **Go 公式のコード規約に従う**: [Effective Go](https://go.dev/doc/effective_go)
2. **コードを整形する**: `go fmt ./...` を実行
3. **コードを検査する**: `golangci-lint` または `go vet ./...` を使用
4. **テストを書く**: 新機能には必ずテストを含める
5. **コメントを付ける**: 公開される関数と型にはドキュメントコメントが必要
6. **定数の命名**: すべての定数は `ALL_CAPS`（UPPER_SNAKE_CASE）スタイルを使用する

コードスタイルの詳細なガイドラインは [CODE_STYLE.md](CODE_STYLE.md) を参照してください。

## 🌐 翻訳ポリシー

Warden はドキュメントと実行時メッセージを 7 言語で提供しています。それらは**すべてが同じ
基準で保守されているわけではありません**。そうであるかのように振る舞うことこそが、5 つの
ロケールが 18 個の翻訳キーと複数のドキュメントを、気づかれないまま取りこぼしていた原因です。

**区分**

| 区分 | 言語 | 期待される水準 |
| --- | --- | --- |
| 正本 | 英語（`enUS`）、簡体字中国語（`zhCN`） | 変更と同じプルリクエストで更新します。挙動を変えたのに両方を更新していない PR は未完成です。 |
| ベストエフォート | `deDE`、`frFR`、`itIT`、`jaJP`、`koKR` | 遅れても構いません。遅れているドキュメントには、読者を正本へ誘導する横断バナーを掲げます。 |

**実行時の文字列はベストエフォートではありません。** `locales/*.json` は
`go test ./locales/` によって強制されており、いずれかのロケールが次に該当する場合は失敗します。

- `en.json` が定義しているキーを欠いている（または `en.json` にないキーを定義している）
- `printf` 動詞（`%s`、`%d`）の並びが英語の原文と異なる
- 値が英語とバイト単位で同一である（未翻訳の文字列）

キーが欠けていても実行時には英語にフォールバックするため、目に見える形では壊れません——
このチェックが存在するのは、まさにそのためです。ユーザーに見えるメッセージを追加するときは、
同じコミットで**7 つすべて**のロケールファイルにキーを追加してください。値が正当に英語と
同一である場合（借用語やプロトコル名など）は、チェックを削除するのではなく、
`locales/locales_test.go` の `intentionallyIdentical` にコメント付きで登録してください。

翻訳済みドキュメントが `enUS` からどれだけ離れているかは `make docs-parity` で確認できます。

## 📦 コミット規約

### コミットメッセージの形式

[Conventional Commits](https://www.conventionalcommits.org/) 規約を採用しています。

```
<type>(<scope>): <subject>

<body>

<footer>
```

### type の種類

- `feat`: 新機能
- `fix`: バグ修正
- `docs`: ドキュメントの更新
- `style`: コード整形の調整（実行結果に影響しない）
- `refactor`: コードのリファクタリング
- `perf`: パフォーマンスの最適化
- `test`: テスト関連
- `chore`: ビルド手順や補助ツールの変更

### 例

```
feat(cache): Add Redis cache support

Implemented Redis-based distributed cache, supporting data persistence and multi-instance sharing.

Closes #123
```

```
fix(router): Fix pagination parameter validation issue

Fixed the issue where incorrect status code was returned when page_size exceeds maximum value.

Fixes #456
```

## 🔄 プルリクエストの流れ

### プルリクエストの作成

```bash
# 1. 機能ブランチを作成
git checkout -b feature/your-feature-name

# 2. 変更を加えてコミット
git add .
git commit -m "feat: Add new feature"

# 3. アップストリームのコードを同期
git fetch upstream
git rebase upstream/main

# 4. ブランチをプッシュして PR を作成
git push origin feature/your-feature-name
```

### プルリクエストのチェックリスト

プルリクエストを提出する前に、次の点を確認してください。

- [ ] コードがプロジェクトのコード規約に従っている
- [ ] すべてのテストが通る（`go test ./...`）
- [ ] コードが整形されている（`go fmt ./...`）
- [ ] 必要なテストが追加されている
- [ ] 関連するドキュメントが更新されている
- [ ] コミットメッセージが[コミット規約](#コミット規約)に従っている
- [ ] コードが lint チェックを通過する

すべてのプルリクエストはコードレビューを受けます。レビューコメントには速やかに対応してください。

## 🐛 バグ報告と機能リクエスト

Issue を作成する前に、既存の Issue を検索し、その問題や機能がまだ報告されていないことを確認してください。

### バグ報告のテンプレート

```markdown
**説明**
バグを明確かつ簡潔に説明してください。

**再現手順**
1. '...' を実行する
2. エラーを確認する

**期待される動作**
期待していた動作を明確かつ簡潔に説明してください。

**実際の動作**
実際に起きたことを明確かつ簡潔に説明してください。

**環境情報**
- OS: [例: macOS 12.0]
- Go バージョン: [例: 1.27]
- Redis バージョン: [例: 7.0]
```

### 機能リクエストのテンプレート

```markdown
**機能の説明**
希望する機能を明確かつ簡潔に説明してください。

**課題の説明**
この機能はどのような問題を解決しますか。なぜ必要ですか。

**提案する解決策**
どのように実現したいかを明確かつ簡潔に説明してください。
```

## 🎯 はじめかた

貢献したいけれど何から手を付ければよいか分からない場合は、次に注目してみてください。

- `good first issue` ラベルの付いた Issue
- `help wanted` ラベルの付いた Issue
- コード中の `TODO` コメント
- ドキュメントの改善（誤字の修正、分かりやすさの向上、例の追加）

疑問がある場合は既存の Issue やプルリクエストを確認するか、関連する Issue で質問してください。
