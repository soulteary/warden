# Warden v1.6.0

This security release requires migration checks before upgrading production.
The Go module remains `github.com/soulteary/warden`, requires Go 1.27.3, and
retains public SDK method signatures and JSON response formats. Security defaults
and accepted network behavior change as described below. Linux remains the
validated build and runtime platform; other cross-compiled binaries are not a
claim of native validation.

## Remote rule sources

Plain and encrypted sources now share a restricted transport. New connections
resolve the configured host, validate every returned address, and dial a checked
address while preserving TLS hostname verification. Redirects are rejected and
environment proxies are ignored. Loopback, link-local, metadata, multicast and
reserved destinations are denied, including through private-origin exceptions.

Production requires verified HTTPS for all remote sources, at startup and in
runtime fetch paths. HTTP remains available in development/test. An encrypted
RSA envelope does not authenticate its publisher; it does not exempt a source
from HTTPS. This release does not add publisher signatures or object anti-rollback.

Before upgrading, migrate HTTP sources to HTTPS with a trusted certificate and
set the final URL rather than a redirecting endpoint. For a legitimate private
source, set `REMOTE_PRIVATE_ORIGINS` to its exact scheme, hostname and effective
port, for example `https://rules.internal:8443`. This does not permit plaintext
production traffic or forbidden local destinations. Public deployments that
require an environment proxy must provide a reachable final source instead.

## Production snapshot reads

`SNAPSHOT_READ_POLICY` defaults to `enforce` in production and `observe` in
development/test. Data endpoints and critical readiness refuse snapshots whose
source freshness cannot be established. Legacy Redis snapshots lack source
success times and cannot establish freshness after recovery; refresh a source
successfully or migrate to V2 snapshots before relying on restored data.
Local rules also need a successful load to establish source evidence.

An explicit `SNAPSHOT_READ_POLICY=observe` preserves the previous availability
policy during a planned migration, while allowing stale directory reads. Set
and verify `SNAPSHOT_MAX_AGE` for the deployment. Snapshot format and recovery
mode defaults remain legacy and bootstrap; this release does not silently
migrate existing Redis data or add source-coverage enforcement.

## SDK authentication and redirects

The SDK rejects every redirect with `ErrRedirect`, including same-origin
redirects. It does not forward credentials or client certificates, retry the
policy rejection, return redirect bodies, or cache them. Configure `BaseURL`
with the final service URL and update callers that depended on redirects.

When an HMAC signer is configured, the SDK omits both `X-API-Key` and bearer
`Authorization`, even if an API key was supplied in its options. This minimizes
reusable credentials on signed requests; it does not change server authentication
policies. API-key-only clients still send both headers. Independent TLS client
certificate configuration is preserved. Validate HMAC configuration before
rolling out clients that previously supplied both credentials; do not rely on
an accompanying API key as fallback for a signed request.

## Optional service permissions

`WARDEN_SERVICE_POLICIES` maps authenticated HMAC key IDs to explicit actions.
It is opt-in; unset policies retain existing server permissions. Enabling it
requires HMAC v2 and distinct secrets for all configured key IDs, denies unmapped
keys, and rejects API-key or client-certificate authentication fallback.
Policies separate lookup, list, log-level administration and authenticated
metrics operations; they do not provide tenant or per-record isolation.

Deploy new key IDs and policies together, test consumers, then remove old
credentials from `WARDEN_HMAC_KEYS` and from client configuration. Omitting an
API-key header in the new SDK does not revoke that API key: remove or rotate old
server-side credentials when they are no longer needed. Keep independent
credentials and instances for mutually untrusted directories. See
[service permissions](../enUS/SERVICE_POLICIES.md) for action names and rollout.

## Compose and existing installations

The Compose example now requires `REDIS_PASSWORD`, configures matching Redis
authentication, and isolates Redis on an internal data network. Update existing
Redis instances and Warden client credentials together; editing the example
alone does not protect an already running deployment. Gateways join only
`auth-internal`. Redis logical databases are not an authorization boundary.
Check the commands and key prefixes required by snapshot and replay modes before
restricting Redis ACLs; Redis snapshot protocol validation currently uses Redis 8.

## Upgrade checklist

1. Configure final HTTPS source URLs and any exact private-origin exceptions.
2. Establish source-success timestamps and verify data/readiness behavior under
   the production enforcement default, including after Redis recovery.
3. Set the SDK final `BaseURL`, verify HMAC consumers, and retire unused secrets.
4. Apply optional service permissions only after checking all consumers and
   monitoring credentials. Update Redis authentication and network isolation.
5. Exercise refresh failures, restart recovery and the intended freshness budget
   before accepting production traffic.
