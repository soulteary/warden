# Warden v1.8.0

This release validates environment variables strictly, splits rate limiting by
authentication result, writes audit records to the application log, adds the
HMAC signature version v3 and corrects how replicas publish to Redis. Some
configurations that started under v1.7.0 are now refused at startup, and
several responses, log lines and metrics change; review the upgrade checks
below before upgrading production.

HTTP routes and the JSON bodies of successful responses are unchanged, with one
exception listed below (an empty list). The v2 Redis snapshot format is
unchanged. The legacy Redis mode adds one key. No data conversion is required.
Dependencies, the Go version (1.27.4) and the build image are those of v1.7.0.
The Go SDK gains methods and options; three SDK behaviors change and are listed
under "SDK consumers".

## New configuration

- `RATE_LIMIT_AUTHENTICATED` and `rate_limit.authenticated_rate` (default 600):
  requests per `RATE_LIMIT_WINDOW` for one credential. The environment variable
  overrides the configuration file. A value below 1 or a non-integer stops
  startup.
- `TRUSTED_PROXY_IPS=none` (case-insensitive, the only entry): no peer is
  trusted, `X-Forwarded-For` and `X-Real-IP` are ignored and the client address
  is the TCP peer. `none` combined with other entries stops startup.
- `WARDEN_HMAC_AUDIENCES`: up to 16 comma-separated names of this instance that
  are accepted in v3 signatures. A name is 1 to 255 printable ASCII characters
  without spaces or commas and is compared in lower case. Empty (the default)
  rejects v3 signatures.
- `WARDEN_HMAC_REQUIRE_AUDIENCE` (default `false`): when true, v1, v2 and
  unversioned signatures are rejected. It requires `WARDEN_HMAC_AUDIENCES` and
  stops startup without it.

See [configuration](../enUS/CONFIGURATION.md),
[security](../enUS/SECURITY.md) and the
[HMAC migration guide](../migration-hmac-v2.md).

## Upgrade checks

### Startup is now refused

Check the environment of every replica before upgrading. Each of these stops
the process with a message that names the setting.

- A boolean environment variable holds a value that is not `true`/`false`,
  `1`/`0`, `yes`/`no`, `on`/`off` or `t`/`f` (any letter case). The variables
  are `REDIS_ENABLED`, `REDIS_TLS_ENABLED`, `HTTP_INSECURE_TLS`,
  `REMOTE_DECRYPT_ENABLED`, `REMOTE_ENCRYPTION_REQUIRED`,
  `REQUIRE_EXPLICIT_USER_ID`, `WARDEN_TLS_REQUIRE_CLIENT_CERT`,
  `WARDEN_HMAC_ALLOW_V1`, `WARDEN_HMAC_REQUIRE_AUDIENCE`,
  `WARDEN_METRICS_REQUIRE_AUTH` and `OTLP_ENABLED`. An empty variable is unset.
  v1.7.0 read an unrecognized value as false for most of them, and
  `WARDEN_METRICS_REQUIRE_AUTH` fell back to the environment default with a
  warning.
- The same change turns settings on. `yes`, `on` and `t` are now read as true
  where v1.7.0 read them as false, for example `REDIS_ENABLED=yes` or
  `REMOTE_DECRYPT_ENABLED=on`. Check that each such value states what the
  deployment intends.
- `PORT` is not an integer from 1 to 65535; `INTERVAL` or
  `WARDEN_HMAC_TIMESTAMP_TOLERANCE` is not an integer of at least 1;
  `HTTP_MAX_IDLE_CONNS` is not an integer of at least 0. v1.7.0 selected the
  default without a message, so `PORT=abc` listened on 8081. `PORT=0`,
  `INTERVAL=0` and `WARDEN_HMAC_TIMESTAMP_TOLERANCE=0`, which selected the
  default, are refused; remove the variable to keep the default.
- `HTTP_TIMEOUT` is not a whole number of seconds or a duration such as `30s`,
  or is outside 1 second to 1 hour. `HTTP_TIMEOUT=0`, which selected the
  default of 5 seconds, is refused. The upper bound of 3600 seconds also
  applies to `--http-timeout` and `http.timeout`.
- `CONFIG` (or `--config`, `remote.url`) is set to
  `http://localhost:8080/data.json`. This address was the built-in default and
  was exempt from validation; it is now validated like any other address and
  refused, because loopback addresses are never accepted as a remote source.
  v1.7.0 could not connect to it either. Remove the setting, or set the address
  of the actual source.
- `MERGE_MODE` is `ONLY_REMOTE` or `REMOTE_FIRST` and no remote address is
  configured. `CONFIG` has no default any more. v1.7.0 started and failed every
  load.
- `ENVIRONMENT=production`, `IP_WHITELIST` is set and `TRUSTED_PROXY_IPS` is
  empty. Set `TRUSTED_PROXY_IPS` to the reverse proxy addresses, or to `none`
  when clients connect to Warden directly. `HEALTH_CHECK_IP_WHITELIST` is not
  part of this rule.
- `RESPONSE_FIELDS` or `app.response_fields` contains a name other than
  `phone`, `mail`, `user_id`, `status`, `scope`, `role`, `name` and
  `dingtalk_userid`. Names are case-sensitive; `email` and `Mail` are refused.
  v1.7.0 accepted such an entry and left the intended field out of every
  response.
- `RATE_LIMIT_AUTHENTICATED`, `WARDEN_HMAC_AUDIENCES` or
  `WARDEN_HMAC_REQUIRE_AUDIENCE` has an invalid value. These variables are new;
  the check matters only when an environment already defines them.

### Remote source

- Without `CONFIG` there is no remote source. `DEFAULT`, `LOCAL_FIRST` and the
  two `*_ALLOW_REMOTE_FAILED` modes then load only the local data, make no
  remote request and are not reported as degraded. Under v1.7.0 such a
  deployment tried the built-in address on every load and logged the failure.
- A background refresh is given `HTTP_TIMEOUT` plus 7 seconds of retry backoff,
  with a minimum of 10 seconds. It was fixed at 10 seconds, which cancelled a
  remote that answered within a longer `HTTP_TIMEOUT`.
- `HTTP_MAX_IDLE_CONNS` is now applied to the remote-source client. The value
  was ignored and the client always used 20, which is now the documented
  default. A deployment that sets the variable gets the value it sets.
- A remote hostname that resolves to an address the connection policy refuses
  fails at once. `warden_refresh_failures_total` reports it with the new
  `reason` value `address_policy`; it was retried until the request timeout and
  counted as a timeout. Add the value to alerts and dashboards that enumerate
  reasons.

### Rate limiting and error responses

- Rate limiting is split by authentication result. Authenticated requests are
  counted per credential against `RATE_LIMIT_AUTHENTICATED` (default 600 per
  window) and no longer consume the per-IP budget. A credential is one HMAC key
  ID, one mTLS client certificate, or the API key together with the client
  address. Requests that fail authentication, anonymous `/metrics` requests and
  unknown paths are counted per client IP against `RATE_LIMIT` (default 60), as
  before.
- Effect with default settings: a gateway that reaches Warden from one address
  is limited to 600 requests per minute per credential, where the address had
  60. Callers of the shared `API_KEY` get 600 per minute per client address. An
  HMAC key ID or a client certificate has one budget across all the addresses
  that use it. A deployment that lowered `RATE_LIMIT` to bound authenticated
  callers must set `RATE_LIMIT_AUTHENTICATED` to keep that bound.
- An address whose per-IP budget is used up by failed authentication receives
  429 before its credential is evaluated, also for requests with a valid
  credential.
- Every 429 response carries `Retry-After`: the seconds, rounded up, until the
  limiter accepts another request. v1.7.0 sent no such header.
- In production, error responses written by the middleware (401, 413, 429 and
  others) are sent with `Content-Type: application/json`. The body was already
  a JSON object but was labelled `text/plain`. Other environments are
  unchanged.
- `warden_rate_limit_hits_total` reports the per-credential limit under
  `scope="credential"`; `scope="ip"` keeps its meaning.
- A list response with no users is `[]` when `RESPONSE_FIELDS` is set. It was
  `null`.

### Logs and traces

- Audit records are written to the application log. Every user query (`/user`,
  `/v1/user`, `/v1/lookup`) and every `POST` or `PUT` to `/log/level` produces
  one JSON line with `"audit": true`. The records were discarded before. The
  line is written at `info` whatever the log level is: neither `LOG_LEVEL` nor
  a level set through `/log/level` filters it. Expect one additional log line
  per query and size log storage accordingly. Phone numbers, mail addresses and
  user IDs in these records are masked.
- `user_id` is masked in the application log and in the trace attributes
  `warden.user.id` and `warden.query.user_id`: the first four characters are
  kept and the rest replaced by `*`. Log searches and trace queries that match
  a full user ID no longer find it.
- The `version` field of every log line is the build version. It was the fixed
  value `0.7.0`. Update log filters that match on it.
- In production the "details hidden" log line is written at `info` for 4xx
  responses and stays at `error` for 5xx. Error-rate alerts that counted these
  lines see fewer of them.
- The message of the first load names no source; the `source` field carries
  it. The message is logged in Chinese: it was `从远程 API 加载数据 ✓`, also for a
  local file, and is now `从已配置的数据源加载数据 ✓`. Log parsers that matched
  the old text need the new text or the field.
- New startup warnings: `TRUSTED_PROXY_IPS` is empty (in every environment; it
  replaces the warning that required `IP_WHITELIST`); no service credential is
  configured outside production; `INTERVAL` is below five seconds; the
  configuration file contains keys that are parsed but not applied;
  `RESPONSE_FIELDS` omits `status`; the Redis database holds keys that Warden
  did not write; production uses Redis without a password; a `user_id` equals
  the phone or mail of a different user. None of them stops startup.
- The behavior with an empty `TRUSTED_PROXY_IPS` is unchanged in this release:
  forwarded addresses are trusted from any private or loopback peer. A later
  release will stop trusting forwarded headers when the variable is empty. Set
  it now to the proxy addresses or to `none`.

### Health checks

- Concurrent health requests share one Redis probe. A healthy result is reused
  for 3 seconds and a failed one for 1 second. A Redis failure can take up to 3
  seconds to appear in the health response and recovery up to 1 second.
- Enforced reads (`SNAPSHOT_READ_POLICY=enforce`) accept a v2 snapshot whose
  source time is up to five seconds ahead of the local clock. Such a reader
  answered 503 until its clock caught up.

### Redis

- Legacy and shadow modes (`REDIS_SNAPSHOT_MODE=legacy`, the default, and
  `shadow`) write the new key `warden:users:cache:source` in the same
  transaction as `warden:users:cache` and `warden:users:cache:version`. A Redis
  ACL that lists Warden's keys one by one must add it before the upgrade.
  Without it the transaction is refused and the shared rule set is no longer
  written; replicas keep serving their in-memory data.
- In these modes the writer first runs a script (`EVALSHA`, and `EVAL` when
  the script is not cached) that calls `GET`, `PEXPIRE`, `PERSIST` and `SET`.
  An ACL that lists commands one by one should permit `EVALSHA` and `PEXPIRE`
  in addition to the commands v1.7.0 used. Where the script is refused, a set
  from a successful load is still written in full on every refresh, and a set
  the replica retained is not written. When Redis already holds the current
  rule set, only its TTL is renewed: the list is not rewritten and
  `warden:users:cache:version` no longer increases on every refresh.
- At startup Warden runs one `SCAN` step to look for keys it did not write. A
  user that is not permitted to run `SCAN` gets a record in `ACL LOG`; the
  check is skipped and startup continues.
- v2 and shadow modes: renewing a snapshot reads only the beginning of the
  stored value with `GETRANGE`. The command is optional. Where the ACL does not
  permit it, the script reads the whole value as before, and each renewal adds
  a denied-command record to `ACL LOG` and to the `acl_access_denied_cmd`
  counter. Grant `+getrange` to avoid that. The other commands are those
  v1.7.0 used; see
  [Redis commands the snapshot store calls](../enUS/REDIS_SNAPSHOT_PROTOCOL.md#redis-commands-the-snapshot-store-calls).
- The Redis writer lock (`warden:rules:refresh`, and the v2 lease) lasts one
  minute while `HTTP_TIMEOUT` is 23 seconds or less, and `HTTP_TIMEOUT` plus 37
  seconds above that. It was one minute in every case. A replica that stops
  during a refresh leaves the lock until it expires; until then the other
  replicas refresh their own data but skip the write to Redis. Keep
  `HTTP_TIMEOUT` no larger than the remote source needs.
- A replica that keeps its last known good rule set after an all-rejected
  refresh no longer writes it over a rule set or snapshot from a later source
  load. This applies to all three modes and depends on replica clocks that
  agree.
- v2 and shadow modes: a snapshot key that is missing, or whose value is not a
  publication of this dataset and policy, is published again by the lease
  holder on its next cycle. Replicas with different snapshot policies that
  share one `REDIS_SNAPSHOT_NAMESPACE` therefore replace each other's snapshot
  on every cycle. Give them separate namespaces, as the
  [migration guide](../enUS/REDIS_SNAPSHOT_MIGRATION.md) requires, before the
  upgrade.

### HMAC signatures

- v2 stays accepted by default and existing clients need no change. v3 binds a
  signature to a name listed in `WARDEN_HMAC_AUDIENCES`. An instance without
  that variable answers 401 to v3 requests, and so does v1.7.0.
- Order: upgrade every replica, set `WARDEN_HMAC_AUDIENCES` on every replica,
  switch clients to v3 (Go SDK: `WithHMACAudience`), and set
  `WARDEN_HMAC_REQUIRE_AUDIENCE=true` only when every client signs v3.

### SDK consumers

- `NewClient` rejects a `BaseURL` without a scheme with `INVALID_CONFIG`. Such
  a value was given `http://`. Add `http://` or `https://` to a bare
  `host:port`.
- A 429 response returns the error code `RATE_LIMITED` with `Error.RetryAfter`.
  It was reported as `REQUEST_FAILED`. The SDK does not retry it. Update code
  that compares error codes.
- A client with `WithTLSConfig` or `WithTLSClientCert` and no transport keeps
  the default transport settings: the proxy environment variables and the
  default connection timeouts apply. It used a transport without them. A client
  that must not use a proxy from the environment needs its own transport.
  `NewClient` no longer modifies the caller's transport.
- New: `CheckUserInListWithError`, which tells "denied" from "Warden could not
  be asked" and returns `INVALID_RESPONSE` when the user response has no
  `status` field; `Lookup` for `GET /v1/lookup`; `WithRequireHTTPS`, which
  refuses to send an API key over plain HTTP to a host other than the local
  machine (off by default; without it the client logs a warning to the
  configured `Logger`); and `WithHMACAudience`. `CheckUserInList` keeps its
  signature and its result.

The root Compose file no longer mounts `/etc/timezone`, and its healthcheck
follows `PORT`.

## Upgrade and rollback

```sh
go get github.com/soulteary/warden@v1.8.0
```

Multi-replica deployments:

1. Before the first replica is replaced, correct the settings listed under
   "Startup is now refused" and extend the Redis ACL (the key
   `warden:users:cache:source`, and `+getrange` for v2). Both changes are
   compatible with v1.7.0.
2. Replace the replicas one at a time, in any order. Do not use the new
   settings (`TRUSTED_PROXY_IPS=none`, `WARDEN_HMAC_AUDIENCES`,
   `WARDEN_HMAC_REQUIRE_AUDIENCE`, the boolean spellings `yes`, `on`, `t`)
   until rollback to v1.7.0 is no longer planned; see below.
3. Upgrade SDK consumers after the service, and enable `WithHMACAudience` only
   after step 4. The v1.8.0 SDK works against a v1.7.0 service as long as it
   signs v2; `Error.RetryAfter` is then zero because v1.7.0 sends no
   `Retry-After`.
4. When every replica runs v1.8.0, set `WARDEN_HMAC_AUDIENCES`, then move
   clients to v3.

A fleet that runs both versions behaves as follows:

- Legacy and shadow modes: a v1.7.0 replica reads and writes
  `warden:users:cache` as before and ignores `warden:users:cache:source`. A set
  it writes has no source record, so a v1.8.0 replica replaces it as v1.7.0
  would. A v1.7.0 replica still writes a retained set over a newer one. The
  protection is complete only when every replica runs v1.8.0.
- v2 mode: the snapshot format and the lease are unchanged, and a v1.7.0
  replica accepts everything a v1.8.0 replica publishes. A v1.7.0 lease holder
  keeps the v1.7.0 behavior: it can publish a retained set over a newer
  snapshot and does not publish again when the key is missing.
- Rate limits are counted in each process. A v1.7.0 replica keeps counting
  every request per client IP against `RATE_LIMIT`.
- The writer lock uses the same key in both versions. A lock taken by a
  v1.8.0 replica can last longer than one minute and is honored by v1.7.0
  replicas.

Rollback to v1.7.0:

- v1.8.0 writes no state that v1.7.0 cannot read. The v1.7.0 binary ignores
  `warden:users:cache:source`, which expires within one hour, and overwrites
  the legacy rule set as it did before. v2 snapshots need no action.
- Replace `TRUSTED_PROXY_IPS=none` first: v1.7.0 refuses to start with it.
  Set the proxy addresses, or remove the variable; with it removed v1.7.0
  trusts forwarded headers from any private or loopback peer.
- Write boolean variables as `true`/`false` or `1`/`0`. v1.7.0 reads `yes`,
  `on` and `t` as false for most variables, without a message, and stops on
  them for `REDIS_TLS_ENABLED` and `WARDEN_HMAC_ALLOW_V1`.
- Move clients back to v2 signatures before the service is rolled back:
  v1.7.0 answers 401 to v3. It ignores `WARDEN_HMAC_AUDIENCES` and
  `WARDEN_HMAC_REQUIRE_AUDIENCE` and accepts v2 again.
- v1.7.0 ignores `RATE_LIMIT_AUTHENTICATED` and
  `rate_limit.authenticated_rate` and counts every request per client IP
  against `RATE_LIMIT`. A gateway that sends more than `RATE_LIMIT` requests
  per window from one address receives 429 again.
- Without `CONFIG`, v1.7.0 uses the built-in address
  `http://localhost:8080/data.json` again and logs a failed remote load on
  every refresh.
- Audit records are no longer written, `user_id` appears unmasked in logs and
  traces, and the `version` log field is `0.7.0` again.
- For SDK consumers, restore the application's pre-upgrade `go.mod` and
  `go.sum`, remove calls to the new methods and options, and rebuild. Verify
  selected versions with `go list -m`.

For versions older than v1.7.0, apply the
[v1.7.0 upgrade checks](v1.7.0.md) and the
[v1.6.0 migration requirements](v1.6.0.md) as well. See the
[Chinese upgrade guide](../zhCN/UPGRADE_V1_8_0.md).

## Verification

Verify the signed tag and source commit, the Go module checksum, the release
workflow run, the asset hashes in `checksums.txt`, the SPDX SBOM, and the image
digest with its keyless signature. `warden --version` prints the version,
commit and build date of a binary, and the `version` field of the log now
carries the same version.
