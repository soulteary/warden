# Warden v1.5.0

This release publishes the main-branch work that was excluded from the v1.4.4
maintenance release. It requires Go 1.27.3. Build and validation remain on Linux;
use Linux containers on other hosts. Cross-compiled binaries do not imply native
validation on their target operating systems.

## Risks and reproduction

- **SDK Scope aliases:** with v1.4.4, cache a user with a non-empty Scope, change a
  Scope element in the returned list, then read the cached list again. The shallow
  nested copy allows the change to reach the cache. Cache writes and reads now
  detach Scope, including cache hits copied outside the lock.
- **Invalidation during a list request:** delay a list response, call ClearCache
  or InvalidateCache, then release that response. Previously it could repopulate
  the invalidated cache. It is now neither returned nor cached and reports
  ErrCacheInvalidated. A cache hit already captured before invalidation may still
  finish returning.
- **Out-of-order responses:** start request A, start and complete B, then complete
  A. A could previously overwrite B. Older responses superseded by a newer
  committed list now report ErrCacheSuperseded. This orders local requests; it is
  not an upstream revision or a remote revocation guarantee.
- **Data age after recovery:** legacy Redis stores no source timestamp. A restart
  can therefore assign recovery-time age to old data. Opt-in V2 snapshots retain
  source_succeeded_at across restore and TTL renewal. Legacy mode keeps its
  existing behavior; upgrading alone does not establish trustworthy source age.
- **Replay-store availability:** configure Redis-backed HMAC replay protection
  with Redis unavailable at startup. Startup now fails rather than silently
  substituting process-local replay protection. When Redis is not configured,
  the existing standalone replay-store behavior is unchanged. Data-cache recovery
  is a separate dependency boundary.

## Changes

Prepared candidates and request-pinned read views keep effective rows, versions
and provenance on one generation. Redis startup recovery remains retryable;
optional stale-replica follow recovery adopts only eligible fresh V2 data after a
failed source refresh and preserves original source time and failure diagnostics.

Optional server strict reads check source freshness on the same snapshot used for
the read and align critical readiness with that decision. Optional SDK source-age
limits use negotiated metadata and the original deadline, including after body
decoding. Qualified absence remains 404; freshness refusal is 503.

Pagination, full reads, early-stop iteration, identity ordering, owned permutation
and hash encoding allocate less. Differential contracts preserve full list order,
InputVersion and EffectiveVersion. Scope is not newly shared across candidate,
index, snapshot or SDK ownership boundaries. Capacity clipping on owned input does
not release an oversized backing array.

Defaults remain legacy Redis snapshots, bootstrap recovery, observe reads and
SDK TTL-based caching without a source-age limit. Plain/encrypted merge and empty
input behavior are unchanged. Follow the
[Redis migration guide](https://github.com/soulteary/warden/blob/v1.5.0/docs/enUS/REDIS_SNAPSHOT_MIGRATION.md)
and [paired freshness configuration](https://github.com/soulteary/warden/blob/v1.5.0/docs/enUS/SDK_SOURCE_FRESHNESS.md)
before enabling the optional policies. Source coverage enforcement is not included.

## Diagnostic compatibility

Source-attempt events are debug-level diagnostics, not coverage or final cache
acceptance evidence. source_id is a source-v1 SHA-256 resource identity;
source_ordinal retains local_1/remote_1 positions. Earlier main snapshots used
ordinals as source_id; v1.4.4 did not emit these events. Update parsers rather than
assuming source_id is a short ordinal. manifest_revision identifies an observed
source-building pass, not a data version. SOURCE_SET_ID scopes resource identities;
changing it changes those identities. Digests are correlatable, not anonymization.

Events include attempt, source_kind, transport, outcome, reason, started_at,
finished_at, decoded_rows, selected_input, winning_rows and load_succeeded.
selected_input and winning_rows describe loader resolution; subsequent validation
can still reject records. Discovery failures and unread sources are not invented
as attempts. Accepted source evidence is process-local; V2 restore leaves it
unknown because the V2 envelope does not store it.

Versioned health metadata supplements the compatibility version/count with known
input_version, effective_version, effective_count and redis_revision. Unknown
fields can be omitted. Snapshot-age metrics advance at collection; V2 age derives
from source_succeeded_at, while publication and restoration have separate times.
Do not compare a source ID, manifest revision or random Redis revision as an
ordered upstream version.

The structured logger still carries its historical service-version value 0.7.0.
Use the release artifact/tag and the startup build-version message to identify
the build; do not interpret that logger field as the release version.

Data JSON bodies remain compatible. Metadata is negotiated with
Warden-Snapshot-Metadata: v1; authenticated data responses vary on that header.
Negotiated freshness 503 responses distinguish expired, unknown and future via
Warden-Source-Error. SDK source-specific error classification is opt-in; ordinary
503 and default SDK error handling retain their existing classification.
ErrCacheInvalidated and ErrCacheSuperseded are new concurrency outcomes that
callers can identify with errors.Is and handle by issuing a new request.

## Historical logs

Validation warnings use stable reason codes and masked identifiers rather than
logging validator error text. This protection already exists in v1.4.4; it is not
a newly fixed v1.4.4 vulnerability. Older builds that logged raw validator errors
may have retained phone numbers or email addresses. A controlled reproduction is
to submit an invalid phone/email record through such a build's validation path
and inspect the rejection warning. Use synthetic data and isolated logs.

Upgrading does not rewrite logs. Operators must inventory affected local logs,
central collectors, exports and backups; restrict access; and redact or remove
sensitive copies under their retention policy, preserving any required incident
records. Rotate credentials if an investigation finds them in historical logs.
Masked values still expose limited structure, such as an email domain, and stable
resource digests can be correlated. Apply access and retention controls to new
logs as well. Source-attempt events omit raw paths, URLs, credentials, payloads
and error text; this is not a claim that every application or proxy log is sanitized.

## Linux validation

Release preparation passed Linux Go 1.27.3 full race tests, real Redis 8 integration,
vet, build, lint and the exact statement-coverage gate. Coverage is 4424/4628
(95.592048%) in CI and 4425/4628 (95.613656%) with the local real-Redis test switch.
Ordering, both version digests, Scope isolation and source-time recovery contracts
pass. All 97 new stage-benchmark variants executed; benchmark timings are not a
production throughput claim. Release artifacts are built and tested by the
[Linux release workflow](https://github.com/soulteary/warden/actions/workflows/release.yml).

## Install

```sh
go get github.com/soulteary/warden@v1.5.0
docker pull ghcr.io/soulteary/warden:1.5.0
```

The release includes Linux, macOS and Windows cross-compiled binaries,
checksums.txt and warden-image-sbom.spdx.json. Verify checksums before use.
The Linux container image is signed with GitHub OIDC; verification details are in
[release security](https://github.com/soulteary/warden/blob/v1.5.0/docs/RELEASE_SECURITY.md).
