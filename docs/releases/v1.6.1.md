# Warden v1.6.1

This patch contains the SDK diagnostic logging fix and current-documentation
corrections merged after v1.6.0. It keeps Go 1.27.3, public SDK signatures, JSON
responses, returned error chains, authentication and storage formats unchanged.
The existing v1.6.0 production defaults still apply; this patch does not introduce
another freshness policy or Redis migration.

## SDK diagnostic logging

With a custom SDK logger enabled, transport failures could include the request
URL and its phone or email query in an error message. Retry diagnostics printed
that URL, and non-200 response diagnostics printed the response body. Internal
failure messages now use allowlisted SDK error categories, HTTP status codes and
fixed text instead of raw transport errors, retry URLs or response bodies.

The default SDK logger remains `NoOpLogger`. This is an existing opt-in logging
exposure, not an authentication bypass. Returned errors retain their existing
details and wrapping, including `errors.Is` behavior. Applications that log
returned errors must apply their own logging policy. The public `Logger`
interface and adapter do not sanitize arbitrary messages supplied by callers.
This patch does not claim that every SDK, application or proxy log is sanitized.

## Documentation corrections

Current English and Chinese data contracts and Redis rollout/rollback guidance
now consistently describe `SNAPSHOT_READ_POLICY=enforce` as the production
default, with `observe` the development/test default. A legacy Redis restore has
unknown source age and returns 503 under enforcement until a source load
succeeds. Changing the Redis storage mode does not change the read policy.
These are corrections to documentation of behavior already present in v1.6.0.
Historical published release notes remain unchanged.

## Upgrade and rollback

```sh
go get github.com/soulteary/warden@v1.6.1
```

- Rebuild SDK consumers to receive the logging fix; upgrading only the Warden
  service does not replace the SDK compiled into another application.
- Review log parsers that depend on raw failure text or retry URLs. Status codes
  and SDK error categories remain available in internal diagnostics.
- Existing logs are not rewritten. Review retention and access to affected logs
  if a custom SDK logger was enabled. Do not infer exposure from the default
  NoOp configuration alone.
- Keep the v1.6.0 deployment configuration, Redis dataset and namespaces. No
  storage conversion is required for this patch.
- Rolling service or SDK code back to v1.6.0 does not change the production read
  default: `enforce` still refuses unknown or expired source evidence. Rolling
  an SDK consumer back restores its earlier diagnostic behavior; disable its
  custom SDK logger or avoid logging those failure paths during rollback.

For an upgrade from a release older than v1.6.0, follow the
[v1.6.0 migration requirements](v1.6.0.md) for verified HTTPS sources, SDK redirect
rejection, credentials, freshness and Redis isolation as well. See the
[Chinese patch upgrade guide](../zhCN/UPGRADE_V1_6_1.md).

## Validation after publication

Verify the signed tag and release commit, official Go proxy resolution, binary
and SBOM checksums, container digest/signature, and the successful release and
quality workflows as described in [release security](../RELEASE_SECURITY.md).
Use isolated test data when exercising logging failures; do not send production
identifiers to a test endpoint. Cross-platform artifacts retain the validation
limits described in v1.6.0.
